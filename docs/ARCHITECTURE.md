# Архитектура «Учебной доски»

## 1. Обзор

«Учебная доска» — веб-приложение с бесконечным холстом для совместных занятий по математике и физике.
Учитель и ученики работают на одной доске в реальном времени, а сервер проверяет права на каждое изменение.

```
                    ┌──────────────────────── Ubuntu 24.04 LTS ────────────────────────┐
                    │                                                                  │
 Браузер            │  ┌───────────────┐        ┌──────────────────────────────────┐   │
 (React SPA)  HTTPS │  │    Nginx      │ /api   │ backend (Node.js 22, Fastify)    │   │
 ───────────────────┼─►│ TLS (certbot) ├───────►│  ├ auth      ├ boards            │   │
  REST  /api/*      │  │ статика SPA   │ /ws    │  ├ users     ├ templates         │   │
  WS    /ws/boards/*│  │ лимиты, gzip  ├───────►│  ├ classes   ├ realtime (Yjs)    │   │
                    │  └───────────────┘        │  └ admin     └ storage (S3)      │   │
                    │                           └───────┬───────────────┬──────────┘   │
                    │                                   │ Prisma        │ S3 API       │
                    │                           ┌───────▼──────┐ ┌──────▼───────┐      │
                    │                           │ PostgreSQL 16│ │    MinIO     │      │
                    │                           │ (том pgdata) │ │ (том minio)  │      │
                    │                           └──────────────┘ └──────────────┘      │
                    └──────────────────────────────────────────────────────────────────┘
```

Все сервисы работают в Docker Compose v2 (`frontend`, `backend`, `postgres`, `minio`) и перезапускаются политикой `restart: unless-stopped`.
Nginx можно поставить на хост или в отдельный контейнер; подробности будут на этапе 9.
Контейнер `frontend` собирает SPA и отдаёт статику через свой лёгкий Nginx. Внешний Nginx занимается TLS, проксирует `/api` и `/ws` и устанавливает лимиты.

## 4. Роли и права

Глобальные роли пользователя: `ADMIN`, `TEACHER`, `STUDENT`. Регистрации нет, все аккаунты создаёт администратор.

На каждой доске у пользователя есть ещё и **роль на доске** (`owner`, `teacher`, `student`, `viewer`, `none`).
Её и набор возможностей (`BoardCapabilities`) вычисляет чистая функция `computeCapabilities` из `@doska/shared/permissions`.
Сервер вызывает её при каждом REST-запросе к доске и при открытии WebSocket, а затем пересчитывает при смене режима, выдаче мела, изменении доступа и блокировке пользователя.

| Тип доски | owner | teacher | student | viewer |
|---|---|---|---|---|
| `LESSON` (урок) | учитель-создатель | соведущий учитель (`BoardMember.CO_TEACHER`) | ученик класса из `BoardClassAccess` или `BoardMember.STUDENT` | администратор, `BoardMember.VIEWER` |
| `NOTEBOOK` (конспект) | ученик-владелец | — | — | учитель класса этого ученика, если ученик открыл конспект (`sharedWithTeachers`); администратор |
| `ASSIGNMENT_WORK` (работа) | учитель, выдавший задание | соведущий | ученик-исполнитель | администратор |
| `TEMPLATE` (шаблон) | автор | соведущий | ученики класса (только просмотр) | учителя, которым шаблон виден; администратор |

Право записи ученика на доске урока зависит от режима:

| Режим | Ученик пишет? |
|---|---|
| Лекция (`LECTURE`) | нет; подсказка: «Сейчас режим „Лекция“…» |
| Совместная работа (`COLLABORATIVE`) | да |
| Выборочно (`SELECTIVE`) | только с «мелом» (`ChalkGrant`) |

Права на уровне объектов задаёт `permissions/object-rules.ts`:
- ученик меняет и стирает только свои объекты; чужие ученические объекты можно трогать только при настройке `allowStudentsEditOthers`;
- учительские объекты ученик трогает только в своей работе по заданию;
- заблокированные объекты (`locked`), фон страницы при `backgroundLocked` и пометки учителя (`layer: 'review'`) защищены от учеников;
- поля `id`, `type`, `createdBy` и `createdAt` неизменяемы; `locked` и `layer` меняет только учитель;
- автор нового объекта обязан совпадать с пользователем соединения.

**Интерфейс никогда не считается защитой.** Клиент использует ту же функцию, чтобы выключать инструменты и показывать подсказки. Решение всегда принимает сервер (см. [SYNC_PROTOCOL.md](SYNC_PROTOCOL.md)).

## 5. Аутентификация и сессии

1. `POST /api/auth/login` принимает логин и пароль, проверенные zod.
   - Rate limit: 10 попыток в минуту с IP и 5 неудач подряд на логин. После этого учётная запись блокируется на 15 минут (`User.lockedUntil`), каждая следующая серия удваивает срок.
   - Хеш проверяется через argon2id. Если логин не существует, сервер всё равно проверяет фиктивный хеш, чтобы время ответа не выдавало, есть ли такой пользователь.
   - Сервер выставляет cookie `access_token` (JWT, 15 мин, `Path=/`), `refresh_token` (случайные 256 бит, 30 дней, `Path=/api/auth`) и `csrf_token` (не httpOnly, для double-submit). У всех cookie флаги `Secure; SameSite=Strict`, у токенов ещё и `HttpOnly`.
   - Событие пишется в `AuditLog` (`LOGIN_SUCCESS` / `LOGIN_FAILED` / `LOGIN_BLOCKED`).
2. Если `mustChangePassword = true`, access-токен содержит claim `pwd: true` (сервер дополнительно сверяет флаг с БД). В таком состоянии доступны только `GET /api/auth/me`, `POST /api/auth/change-password` и `POST /api/auth/logout`, а WebSocket закрывается с кодом `4428`.
3. `POST /api/auth/refresh` ротирует refresh-токен. В БД хранится только SHA-256 токена. Если предъявлен уже отозванный токен, отзывается вся семья (`familyId`) и пишется `TOKEN_REUSE_DETECTED`.
4. **CSRF.** Каждый изменяющий REST-запрос обязан передать заголовок `X-CSRF-Token`, равный cookie `csrf_token` (double submit). Дополнительно действуют `SameSite=Strict` и проверка `Origin`/`Referer` против `PUBLIC_ORIGIN`. У WebSocket при upgrade проверяется `Origin` (защита от CSWSH).
5. Блокировка или удаление пользователя отзывают все его refresh-токены и через внутреннюю шину событий мгновенно закрывают его WebSocket-сессии (`4423`). Access-токен живёт не дольше 15 минут, а middleware дополнительно сверяет `isBlocked`/`deletedAt` с кэшем на 30 с.

## 6. Хранение данных

- **PostgreSQL** хранит пользователей, классы, доски (метаданные), доступы, задания, шаблоны, версии и журнал. Схема описана в [`backend/prisma/schema.prisma`](../backend/prisma/schema.prisma).
- **Содержимое доски** — это Yjs-документ (см. [BOARD_MODEL.md](BOARD_MODEL.md)):
  - `BoardDocument.state` хранит сжатый снимок `Y.encodeStateAsUpdate`;
  - `BoardUpdate` — журнал принятых сервером обновлений. Он пишется пакетами раз в 1 с, поэтому при падении процесса теряется не больше секунды работы;
  - компактация раз в 60 с или после 500 записей: снимок и хвост журнала сливаются в новый снимок, вошедшие записи удаляются, и всё это происходит в одной транзакции;
  - `BoardVersion` содержит полные снимки для истории версий: автоматически каждые 10 минут активного редактирования, вручную, а также перед восстановлением и перед массовой очисткой. Хранятся последние 50 автоматических и все ручные.
- **MinIO** (или каталог `UPLOADS_DIR`, если `S3_ENDPOINT` пуст) хранит картинки и PDF. Бакет приватный, содержимое отдаёт бэкенд вошедшим пользователям по случайному UUID файла. Ключи вида `assets/<год>/<месяц>/<uuid>.<расширение>` генерирует сервер.
- **Миниатюры** рисует браузер из документа доски: в сетке работ — по облегчённым подпискам `?lite=1`, в списках досок — по снимку `GET /api/boards/:id/snapshot` (этап 4.2). Изображения миниатюр не хранятся.

## 7. Синхронизация в реальном времени (кратко)

Полное описание — в [SYNC_PROTOCOL.md](SYNC_PROTOCOL.md).

- Один WebSocket на открытую доску: `/ws/boards/:boardId`. Кадры совместимы с y-protocols (sync, awareness), плюс управляющие JSON-сообщения (тип 100).
- Сервер **авторитетен**. Каждое Yjs-обновление клиента он применяет к своей копии документа, разбирает изменения по объектам и полям, проверяет `object-rules` и всё запрещённое сразу **компенсирует** обратной правкой от имени сервера. Остальные клиенты получают объединённое обновление, в котором запрещённого изменения уже нет. Такая схема не ломает CRDT-историю, в отличие от простого «отклонить пакет». Подход проверен прототипом при проектировании.
- Офлайн-работа: Y.Doc клиента хранится в IndexedDB (`y-indexeddb`). После переподключения стандартный обмен sync step1/step2 отправляет накопленные изменения, и они проходят ту же проверку. Индикатор показывает состояния «онлайн», «переподключение…» и «офлайн (N изменений ждут отправки)».
- Undo/Redo реализован через `Y.UndoManager` с `trackedOrigins = {локальный origin}`, поэтому отменяются только собственные действия. Глубина истории — 200 шагов (ТЗ требует минимум 100).
- Присутствие (курсоры, выделения, лазер, рисуемый штрих) передаётся через awareness. Имя, цвет и роль подставляет сервер.

## 8. Фронтенд: ядро холста

- **Камера** задаётся мировыми координатами центра и зумом от 1 % до 10 000 %. Зум колесом и щипком, панорамирование пробелом с мышью, средней кнопкой или двумя пальцами.
- **Слои Konva** (снизу вверх):
  1. фон (сетка рисуется одним `Shape` с `sceneFunc` и зависит только от камеры);
  2. объекты слоя `background`;
  3. объекты `content` и `review` с виртуализацией по видимой области;
  4. активный слой: перетаскиваемые и редактируемые объекты, чтобы не перерисовывать всё;
  5. оверлей: рамка выделения, ручки, подсказки привязок, курсоры, лазер, чужие недорисованные штрихи.
- **Производительность при 1000+ объектах:**
  - пространственный индекс R-tree (`rbush`) по мировым габаритам, обновляемый инкрементально по событиям Yjs;
  - рендерятся только объекты, пересекающие видимую область с запасом 20 %;
  - `hitTest` вызывается только для кандидатов из индекса;
  - статичные сложные объекты (формулы, графики, поля) кэшируются растром (`node.cache()`) с учётом зума: при изменении масштаба более чем в 1,5 раза кэш перестраивается, поэтому формулы остаются чёткими;
  - **кэш растров формул**: ключ — `(latex, цвет, ступень масштаба)`, LRU на 500 записей. KaTeX → SVG → `HTMLImageElement`;
  - штрихи хранятся как плоские массивы `[x, y, нажатие, …]`, упрощаются алгоритмом Рамера — Дугласа — Пекера при сохранении и рисуются одним `Path2D`;
  - подписка на Yjs поштучная: изменение одного объекта перерисовывает только его React-компонент (селекторы по id).
- **3D-сцены.** Браузер разрешает около 16 WebGL-контекстов, поэтому неактивная 3D-сцена на доске отображается кэшированным снимком (один общий offscreen-рендерер). Двойной клик «оживляет» её: поверх холста в рамке объекта монтируется `<Canvas>` react-three-fiber. Камера сцены синхронизируется в режиме «Следуйте за мной».
- **Web Workers.** Силовые линии, ОДУ, цепи, ход лучей, неявные кривые и поверхности считаются в пуле воркеров (`solvers/worker-pool.ts`) с отменой устаревших заданий. Результат кэшируется по хешу входных данных. Модули объектов объявляют `compute` (см. [PLUGINS.md](PLUGINS.md)).
- **Темы.** Светлая, тёмная и «меловая доска». Объекты хранят семантические цвета (`ink`, `accent-1`…`accent-8`) или hex. `ink` в светлой теме чёрный, а в тёмной и меловой — белый. Остальные семантические цвета подобраны контрастными для каждой темы.

## 9. Безопасность

- Все входные данные REST и WebSocket проверяются zod-схемами (`@doska/shared`, `backend/src/**/schemas.ts`).
- Ограничения размеров: тело JSON до 1 МБ; кадр WS до 4 МБ; awareness до 64 КБ; `props` объекта до 512 КБ; до 50 000 объектов на доске; картинки до 15 МБ; PDF до 50 МБ и 300 страниц.
- Загрузки проверяются по содержимому (`backend/src/assets/sniff.ts`): PNG, JPEG, GIF, WebP, PDF. SVG запрещён (XSS): браузер перед загрузкой превращает его в PNG.
  - Метаданные картинок (EXIF с координатами, XMP, IPTC, комментарии) сервер вырезает при разборе структуры файла, без перекодирования и без нативных библиотек. Повреждённый файл отклоняется, размер изображения ограничен (12 000 пикселей по стороне, 100 Мп).
  - Браузер дополнительно перекодирует картинки (поворот по EXIF, не больше 4096 пикселей по стороне).
  - Файлы отдаются с `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox`.
  - PDF на сервере не разбирается и не растеризуется: страницы рисует браузер (pdf.js) в масштабе экрана. Так текст чёткий при любом увеличении, а на сервере не нужен внешний растеризатор.
- Поверх Nginx действуют rate limits Fastify (`@fastify/rate-limit`): вход, refresh, загрузки, WS-сообщения (токен-бакет на соединение).
- Логи пишет pino с `redact` для `req.headers.cookie`, `authorization`, `*.password`, `*.token`, `*.passwordHash`, `set-cookie`. Пароли и токены не попадают ни в логи, ни в `AuditLog.details` (там функция `sanitizeDetails`).
- Текст и формулы рендерятся без `innerHTML`: rich text — из JSON-дерева через React, KaTeX с `trust: false` и `maxExpand`.
- Заголовки (Nginx): `Content-Security-Policy` (без `unsafe-eval`; картинки и PDF — с того же домена, `/api/assets`), `X-Content-Type-Options`, `Referrer-Policy`, HSTS.

## 10. Масштабирование и ограничения

Целевая нагрузка — школа или кафедра: сотни пользователей, десятки одновременных уроков по 30–40 участников.
Один процесс backend держит комнаты досок в памяти: документ выгружается через 30 с после ухода последнего участника.
Для горизонтального масштабирования модуль `realtime` изолирован интерфейсом `RoomBus`. Сейчас это реализация в памяти; позднее можно добавить реализацию на Redis pub/sub с маршрутизацией комнаты на один узел по `boardId`. В рамках ТЗ это не требуется.

## 11. Распознавание рукописных формул

Это подключаемый сервис. Если переменная `FORMULA_OCR_URL` пуста, кнопка «Распознать формулу» скрыта.
Бэкенд проксирует запрос `POST /api/recognition/formula`, принимая PNG выделенных штрихов (не больше 2 МБ) и пересылая его во внешний сервис. Поддерживаются совместимые с Mathpix API сервисы и self-hosted pix2tex/LaTeX-OCR в HTTP-обёртке. Ключ API хранится только на сервере, и пользователь подтверждает отправку изображения во внешний сервис.
