# Протокол синхронизации

Типы и схемы описаны в `packages/shared/src/protocol/`: `messages.ts` и `codec.ts`.
Текущая версия протокола — `PROTOCOL_VERSION = 1`.

## 1. Подключение

```
Клиент                                                     Сервер
  │  GET /ws/boards/:boardId  (Upgrade: websocket)            │
  │  Cookie: access_token=…;  Origin: https://doska.example   │
  │──────────────────────────────────────────────────────────►│ 1. Origin ∈ PUBLIC_ORIGIN, иначе 403
  │                                                           │ 2. JWT из cookie: подпись, срок, pwd_change
  │                                                           │ 3. Пользователь не заблокирован/не удалён
  │                                                           │ 4. computeCapabilities(...).view, иначе 403
  │◄─────────────────────────── 101 Switching Protocols ──────│
  │  [100] hello {protocol, sessionId, yClientId}             │
  │──────────────────────────────────────────────────────────►│ protocol ≠ 1 → close 4426
  │                                                           │ та же sessionId уже подключена → старое close 4409
  │◄── [100] session.init {user, board, capabilities, chalkHolders, hands, follow, serverTime}
  │◄── [0]   sync step1 (state vector сервера)                │
  │◄── [1]   awareness (состояния всех участников)            │
  │  [0] sync step1 (state vector клиента)                    │
  │──────────────────────────────────────────────────────────►│
  │◄── [0]   sync step2 (то, чего нет у клиента)              │
  │  [0] sync step2 (то, чего нет у сервера: офлайн-правки)   │
  │──────────────────────────────────────────────────────────►│ → проверка (раздел 3)
  │          … далее [0] update, [1] awareness, [100] control в обе стороны
```

Ошибки на этапе upgrade возвращаются HTTP-статусом (401, 403, 404).
Ошибки после upgrade приходят кодами закрытия `CloseCode` (раздел 9).
Если клиент получил `4401`, он вызывает `POST /api/auth/refresh` и переподключается.

## 2. Формат кадров

Все кадры бинарные. Первый `varuint` — тип сообщения:

| Тип | Содержимое | Направление |
|---|---|---|
| `0` Sync | y-protocols/sync: `step1(sv)`, `step2(update)`, `update(update)` | ⇄ |
| `1` Awareness | y-protocols/awareness: `encodeAwarenessUpdate` | ⇄ |
| `3` QueryAwareness | пусто: запрос полного состояния awareness | → |
| `100` Control | `varString(JSON)`; схема `clientControlSchema` / `serverControlSchema` | ⇄ |

Типы 0, 1 и 3 совпадают с y-websocket, поэтому клиент использует стандартные функции `y-protocols`.

## 3. Проверка Yjs-обновлений на сервере

### 3.1. Почему не «отклонить пакет целиком»

Обновление Yjs несёт элементы с идентификаторами `(clientID, clock)`, и clock клиента растёт строго последовательно.
Если сервер просто выбросит обновление клиента, у него образуется «дыра» в последовательности clock этого клиента, и **все** следующие обновления клиента сервер не сможет применить: они попадут в `pendingStructs` навсегда.
Клиенту пришлось бы пересоздавать документ и терять все несохранённые офлайн-правки, включая разрешённые.

### 3.2. Схема «применить → проверить → компенсировать»

Сервер — авторитетный участник CRDT:

```
onSyncUpdate(conn, update):
  если размер > 4 МБ или формат битый → close 4413/4500
  если parseUpdateMeta(update).from[c] > stateVector[c] для какого-то c
     (обновление ссылается на элементы, которых у сервера нет), не применять
     и закрыть соединение с 4500. У корректного клиента так не бывает:
     соединение упорядочено, а step2 содержит всё недостающее. После
     переподключения клиент пришлёт полный step2, и проверка пройдёт
     обычным путём. Так в документе сервера не остаётся отложенных
     структур (pendingStructs), которые нельзя проверить
  violations = []
  doc.transact(() => Y.applyUpdate(doc, update), conn)  // origin = соединение
      ├─ observeDeep(objects/pages/meta) с tr.origin === conn собирает изменения
      │   (YMapEvent.changes.keys с action и oldValue), значения удалённых
      │   Y.Map читаются до сборки мусора (в обработчиках событий содержимое
      │   ещё доступно)
      └─ для каждого изменения вызываются правила object-rules.ts
         с правами conn.capabilities → нарушения попадают в violations
  если violations не пуст:
      doc.transact(() => compensate(violations), SERVER)
      conn ← notice {code: 'CHANGE_REVERTED', reason, objectIds}
  разослать накопленные doc.on('update') всем остальным одним
      Y.mergeUpdates([...]) — запрещённое изменение и его отмена
      применяются у них атомарно и ни на миг не видны
  отправителю — только компенсирующую часть
  поставить обновления в очередь на сохранение (раздел 7)
```

Компенсация — обычная правка от имени сервера (отдельный `clientID` сервера), поэтому история CRDT остаётся согласованной у всех. Нарушитель получает её как обычное обновление, и его локальная копия возвращается к допустимому состоянию.
Последующие правки этого клиента применяются нормально, без «дыр» в clock.

| Нарушение | Компенсация |
|---|---|
| Создан объект без права (`canCreateObject`) | удалить ключ из `objects` |
| Создан объект с полями вне схемы (`boardObjectSchema`, лишние поля, вложенные Y-типы, `props` > 512 КБ, превышен лимит объектов) | удалить ключ |
| Неверный `createdBy` | удалить объект (`AUTHOR_MISMATCH`) |
| `createdAt` в будущем более чем на 1 мин | исправить на время сервера |
| Изменено поле без права (`canUpdateObjectField`) или недопустимое значение (`objectFieldSchemas`) | вернуть `oldValue` поля (или удалить поле, если его не было) |
| Удалён объект без права (`canDeleteObject`) | заново создать `Y.Map` с прежними полями (снимок из `oldValue`) |
| Изменение `pages` без права (`canCreatePage` / `canEditPage`) | вернуть прежнее значение / удалить / пересоздать страницу |
| Любое изменение `meta` или корней вне `meta/pages/objects` | откат (корни вне списка очищаются) |

Наблюдатель на корне `objects` получает **один** `YMapEvent` на транзакцию с полным списком изменённых ключей, поэтому проверка стоит O(число изменённых полей), а не O(размер документа).
Сервер держит индекс `objectId → ObjectGuardInfo` (автор, `locked`, `layer`, `pageId`, `authorIsModerator`), который обновляется после каждой принятой транзакции.

### 3.3. Гонки при смене прав

Если учитель переключил режим на «Лекция», пока ученик рисовал, обновление ученика проверяется уже с **новыми** правами.
Штрих будет компенсирован, а ученик получит `notice` и `capabilities`.
Клиент заранее выключает инструменты, как только получает `capabilities`, поэтому такие ситуации редки и затрагивают одно-два действия.

### 3.4. Сборка мусора

Документ на сервере создаётся с `gc: true`: содержимое удалённых и компенсированных элементов не хранится и не уходит новым клиентам.
История версий не опирается на `Y.snapshot`, вместо этого используются полные снимки `BoardVersion`.

## 4. Awareness (присутствие)

Состояние клиента описывает `awarenessStateSchema`:
- `cursor` — курсор в мировых координатах; отправляется не чаще 30 раз в секунду;
- `selection` — id выделенных объектов (другие видят рамки цвета пользователя);
- `tool` — текущий инструмент (подпись у курсора);
- `editing` — объект, который пользователь сейчас редактирует. Это мягкая блокировка: у других на объекте видна плашка «Редактирует Иванов И.»;
- `viewport` — вид пользователя (учитель видит, кто где находится);
- `laser` — след лазерной указки, до 400 точек с метками времени; угасает за 1,5 с;
- `drawing` — незавершённый штрих, до 4000 точек.

Сервер для каждого входящего кадра awareness:
1. разбирает обновление и проверяет, что в нём только `clientID` этого соединения, состояние до 64 КБ и проходит схему; иначе кадр отбрасывается;
2. **подменяет** `user` данными сессии: id, ФИО, роль, цвет;
3. обнуляет `laser`, если `capabilities.laser = false`, и `drawing`, если `write = false`;
4. если включена настройка `showStudentCursors = false`, состояние ученика отправляется только учителям доски;
5. рассылает результат.

При отключении соединения сервер удаляет состояния его `clientID` (`removeAwarenessStates`).
Список присутствующих — это уникальные `user.id` из awareness. Учитель видит вкладку «Участники» с ролями, мелом и поднятыми руками.

## 5. Управляющие сообщения

### Клиент → сервер

| `t` | Кто | Действие сервера |
|---|---|---|
| `hello` | все | проверка версии, привязка `yClientId` к пользователю, ответ `session.init` |
| `ping` | все | `pong` (используется и для оценки задержки и смещения часов) |
| `mode.set` | `manageLesson` | `Board.mode` в БД, `AuditLog BOARD_MODE_CHANGED`, всем `mode.changed`, каждому пересчитанные `capabilities` |
| `chalk.set`, `chalk.revokeAll` | `manageLesson` | `ChalkGrant` в БД, всем `chalk.changed`, затронутым `capabilities`; выдача мела опускает руку ученика |
| `follow.start/update/stop` | `leadFollow` | хранит состояние в памяти комнаты, всем `follow.state`; `update` не чаще 15 Гц |
| `hand.raise`, `hand.lower` | `raiseHand` | список рук в памяти комнаты, всем `hands`; учитель получает звуковое и визуальное уведомление |
| `hand.dismiss` | `manageLesson` | снять руку ученику |
| `objects.clearByAuthors` | `clearStudentObjects` | снимок `BoardVersion(BEFORE_CLEAR)`, затем одна серверная транзакция удаления; всем `notice BOARD_CLEARED` |
| `settings.set` | `manageLesson` | `Board.settings` в БД, всем `settings.changed`, пересчёт `capabilities` |

Сервер отвечает на неразрешённое управляющее сообщение `error {code: 'FORBIDDEN'}` и ничего не меняет.

### Сервер → клиент

`session.init`, `pong`, `capabilities`, `mode.changed`, `chalk.changed`, `follow.state`, `hands`, `settings.changed`, `notice`, `error` — схема в `serverControlSchema`.

## 6. «Следуйте за мной»

Учитель отправляет `follow.start {viewport, strict}`, затем `follow.update {viewport, scenes}` при каждом изменении камеры (не чаще 15 Гц) и `follow.stop`.
`viewport` — это страница, мировой центр экрана и зум. Клиент ученика вписывает ту же **мировую область** в свой экран, сохраняя центр и подгоняя масштаб под размер окна, и анимирует переход за 150 мс.
`scenes` — камеры активных 3D-сцен: позиция, цель, up и zoom.
Если `strict = false`, ученик может временно отойти: тогда появится кнопка «Вернуться к учителю». Если `strict = true`, панорамирование и зум у ученика отключены.
Новые подключения получают текущее состояние в `session.init.follow`.

## 7. Сохранение

```
принятое обновление ─► очередь комнаты ─(каждую 1 с)─► INSERT BoardUpdate(mergeUpdates(пакет))
                                         │
                       каждые 60 с или 500 записей:
                       BEGIN; state = encodeStateAsUpdate(doc);
                       UPSERT BoardDocument(state, sv, compactedSeq);
                       DELETE BoardUpdate WHERE seq <= compactedSeq; COMMIT
                                         │
                       каждые 10 мин активного редактирования: INSERT BoardVersion(AUTO)
```

- Загрузка комнаты: `BoardDocument.state` и затем все `BoardUpdate` с `seq > compactedSeq` по порядку.
- Выгрузка комнаты: через 30 с после ухода последнего участника — финальная компактация.
- При `SIGTERM` (обновление или перезапуск) все комнаты сохраняются, затем клиенты получают `4503` и переподключаются, когда сервер поднимется.
- `Board.objectCount`, `pageCount` и `lastActivityAt` обновляются при компактации.

## 8. Офлайн-режим, переподключение, undo

- Клиент хранит `Y.Doc` в IndexedDB (`y-indexeddb`, база `doska:<boardId>:<userId>`). Изменения, сделанные без связи, применяются локально и сохраняются, даже если вкладку перезагрузили.
- Переподключение идёт с экспоненциальной задержкой и случайным разбросом: 0,5 → 1 → 2 → 4 → … → 30 с. При событии `online` браузера попытка выполняется сразу. Коды из `TERMINAL_CLOSE_CODES` не переподключаются: пользователю показывается причина.
- После переподключения обмен sync step1/step2 отправляет накопленное, и всё проходит проверку из раздела 3.
- Индикатор соединения: «В сети» (зелёный), «Переподключение…» (жёлтый), «Нет связи — изменения сохранены локально (N)» (серый). N — число локальных транзакций, которые сервер ещё не подтвердил. Подтверждение определяется сравнением state vector сервера с локальным.
- Undo/Redo: `Y.UndoManager(objects, pages)` с `trackedOrigins = new Set([LOCAL_ORIGIN])` и `captureTimeout = 400` мс. Отменяются **только собственные** транзакции; чужие и серверные не трогаются. Глубина — 200 шагов. Если отмена затрагивает объект, который учитель с тех пор заблокировал, сервер её компенсирует, и пользователь видит `notice`.

## 9. Коды закрытия

| Код | Значение | Переподключаться? |
|---|---|---|
| 4401 | нет или истёк access-токен | да, после refresh |
| 4403 | нет доступа или доступ отозван | нет |
| 4404 | доска не найдена или удалена | нет |
| 4409 | доска открыта этой же вкладкой заново | нет |
| 4413 | слишком большое сообщение | да |
| 4423 | учётная запись заблокирована | нет (выход) |
| 4426 | версия протокола не поддерживается | нет (перезагрузить страницу) |
| 4428 | нужно сменить временный пароль | нет (страница смены пароля) |
| 4429 | превышен лимит частоты | да, с задержкой |
| 4500 | внутренняя ошибка | да |
| 4503 | сервер перезапускается | да |

## 10. Ограничения частоты (на соединение)

| Поток | Лимит |
|---|---|
| Sync update | 60 кадров/с в пике, 20/с в среднем, 2 МБ/с |
| Awareness | 40 кадров/с |
| Control | 20 сообщений/с |

При превышении сервер сначала отправляет `notice SLOW_DOWN`, а при повторном превышении в течение 10 с закрывает соединение с кодом `4429`.

## 11. Сетка работ учеников (раздача задания)

Учитель открывает `GET /api/assignments/:id/works`: список работ со статусами и URL миниатюр.
Для работ, видимых на экране (до 40), клиент открывает **облегчённые** подписки `/ws/boards/:workBoardId?lite=1`. В этом режиме сервер не шлёт awareness, а клиент рисует миниатюру из документа с упрощённым рендерингом.
Так сетка обновляется в реальном времени без загрузки всех работ сразу.
По клику работа открывается целиком: учитель пишет в неё пометки в слое `review` другим цветом (по умолчанию красным), и ученик их видит, но изменить не может.

## 12. История версий и восстановление

Восстановление — это **не замена документа**, а семантическая правка поверх текущего состояния. Так CRDT-история не ломается, и у всех клиентов всё применяется как обычное обновление:

```
BoardVersion(BEFORE_RESTORE) ← текущее состояние
target = Y.Doc из BoardVersion.state
doc.transact(() => {
  для каждого объекта/страницы текущего документа, которого нет в target → удалить
  для каждого объекта/страницы из target:
     нет в текущем → создать; есть и отличается → записать различающиеся поля
}, SERVER)
```
